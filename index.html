番茄小说榜单自动分析

02

定期记录番茄小说榜单与作品简介，分析题材和排名变化，再把简报发送到自己的邮箱。

外部输入榜单 + 公开作品简介
建议节奏每日 16:00 采集
交付成果自动运行的录屏
作业必须包含三个环节

定期采集外部输入；让 Agent 遍历自己授权的数据目录，建立数据与技能地图；结合两者自动分析，并把结果邮件发给自己。只展示榜单页面还不够。

SOURCE

先明确“榜单”和“内容”

以番茄小说官网公开排行榜为入口，选择固定分类的阅读榜或新书榜，建议每日保存前 20 本。

官网说明榜单按在读数据排序，每天下午 3 点前更新上一日排名。这里将其称为“排行榜”，不把它描述成未公开的个性化推荐算法。

作品“大概内容”以公开简介为依据，生成简短题材说明。简介没有的信息写“未提供”，不推断完整剧情。

打开番茄小说官方榜单
DATA CONTRACT

每条记录保存什么

采集时间榜单日期榜单 / 分类排名作品 ID书名 / 作者在读人数原文连载状态公开简介来源 URL

作品 ID 是稳定标识；“在读人数”不是销售额。保留人数原文和标准化值，不同分类、不同榜单分别比较。

WORKFLOW

从采集到邮件的六步流程

  1. 建立可重复的采集器

    先验证公开页面能否正确解析；动态页面可用 Playwright 读取浏览器实际展示的内容。只采集公开榜单和简介，设置低频访问、超时、有限重试与本地快照；遇到验证码或访问限制则记录失败，不继续重复请求。

    官网文本可能使用特殊字体编码，应把解析结果与浏览器中的书名、数字逐项核对；出现乱码时先修复解析，不能让模型猜字。

  2. 保存每日快照

    用 SQLite 或 CSV 保存记录，以“榜单日期 + 分类 + 作品 ID”去重。保留原始页面及采集日志；抓取失败与“榜单没有变化”要分开标记。

  3. 生成自己的数据与技能地图

    让 Agent 扫描指定的学习与研究目录，记录可用数据、字段、已有分析脚本和用过的方法，输出 data_skill_map.md。不把密钥、私人邮件或无关文件加入分析。

  4. 脚本计算，模型解释

    脚本计算新入榜、离榜、同榜排名变动及题材占比；模型根据简介提取题材标签，写 80—120 字梗概，并结合技能地图建议分析方法。至少有两天快照后才计算日变化。

  5. 定时触发并发送给自己

    Windows 任务计划程序每日运行采集 → 分析 → 邮件流程。邮件包含采集时间、题材摘要、排名变动和原始链接。SMTP 凭据由环境变量读取，失败要有日志。

  6. 录制完整运行过程

    手动触发一次同样的定时任务，录到采集、分析完成及自己的邮箱收到结果。等待部分可以加速，画面中遮盖密钥和个人信息。

正式提交：导出的运行录屏，证明触发后系统自动完成并发送结果。

建议留存：采集与分析脚本、两天以上的快照、数据与技能地图、任务配置、运行日志和邮件截图。分析深度不是替代链路实际运行的条件。

游戏行业财报知识库

03

选择作业 3 的知识库路线，用游戏公司年报与半年报建立可引用、可比较的问答系统。

覆盖范围10 家以上公司
检索方式向量 + BM25
评测要求10 问 / 至少 2 个全景问题
REQUIREMENTS

正式要求

  • 从交易所网站取得年报或半年报全文。
  • 提取正文，恢复表格行列结构。
  • 文本块保留公司、章节和页码。
  • 建设向量索引及 BM25 索引。
  • 交互式问答页的答案引用原文来源。
  • 10 个评测问题逐项记录检索块、正确性与失败原因。

本项目选择选项 A，不需要同时完成微调选项 B；GraphRAG 也不是这一选项的必做要求。

RESEARCH SCOPE

先统一财报口径

建议从同一报告年度开始，再扩展到多年度。选择游戏业务相关的上市公司，并核对各家公司游戏业务的披露口径。

跨公司比较时统一年度、货币、单位和合并范围。集团收入不能直接当作游戏收入；“未披露”不能记作 0。

WORKFLOW

建设与验收

  1. 建立报告清单

    从上交所、深交所的披露渠道下载全文，巨潮资讯可用于检索定位。记录公司、年份、报告类型、原始 URL 和文件哈希，排除摘要及重复或被更正的旧版本。

  2. 提取正文与表格

    优先读取 PDF 文本层，扫描页再做 OCR。财务表格保留表名、列名、单位、年度和附注；同时记录 PDF 页序号及印刷页码，人工核对关键数字。

  3. 按章节切块并保留元数据

    不要截断表格。保存 company / year / report_type / section / pdf_page / printed_page / table_id / source_url，使每个文本块都能返回原报告。

  4. 建设两套索引

    使用中文向量模型生成嵌入，配合 FAISS 或 Chroma；对同一批块建立中文分词的 BM25。查询先按公司与年份过滤，再合并向量和关键词结果，去重并保留命中记录。

  5. 回答必须由证据支持

    单公司问题检索相关章节；全景问题拆成逐公司查询，检查每家公司是否覆盖后再汇总。答案显示“公司 + 报告年度 + 页码 + 原文链接”；缺少证据就明确缺项。

  6. 用固定问题评价

    保存问题、命中块、生成答案、人工参考答案、正确性及失败原因。分别统计检索遗漏、口径错误、计算错误和无证据回答，不用“看起来合理”代替核对。

  3. 吉比特主要产品贡献有哪些，报告给出了哪些相关指标？
  4. 恺英网络的研发支出及其披露口径是什么？
  5. 世纪华通海外业务在报告中如何披露？
  6. 巨人网络的销售费用同比变化及报告中的解释是什么？
  7. 游族网络主要风险因素中哪些与游戏业务有关？
  8. 冰川网络的经营现金流与归母净利润分别是多少？
  9. 全景 同年度各公司披露的游戏业务收入如何比较？列明单位、口径和未披露项。
  10. 全景 各公司海外业务布局及相关风险有何异同？逐公司给出证据。

本地模型微调与判案 API

04

用课程判决数据制作训练样本，微调中文模型，再将本地推理封装为符合老师协议的公网接口。

课程数据3,520 篇民事一审判决
建议模型Qwen2.5-7B-Instruct
正式验收10 案 / 每案 ≤ 120 秒
先交付接口，再评价模型

作业 4 的正式评价是完成 / 未完成：接口可连通，10 个新案例都返回四项结果。准确性、法条依据和微调收益要另行评测，不能把“接口通过”当成“预测正确”。

MODEL CHOICE

本地微调的起点

优先尝试 Qwen2.5-7B-Instruct + 4-bit QLoRA：选择中文指令模型，用量化冻结基础参数，只训练 LoRA 适配器，降低训练资源需求。

显存不足可先用 Qwen2.5-3B-Instruct走通数据、训练与接口。模型大小只是起点，最终按验证集质量和实际响应时间选择。

硬件尚未确定。7B 可先在 16—24 GB 显存环境做小批量试跑，这是规划估计，不是显存保证；序列长度、批量和实现都会影响需求。Windows 可使用 WSL2 + CUDA，先验证依赖兼容性。

TRAINING TARGET

训练什么，不泄漏什么

judgments.jsonl 每行只有 id 和 text。从全文制作标签，以“本院认为”之前的事实部分作为输入，案由、法条、方向和判决主文作为目标。

结果和裁判理由可以用来审核标签，不能混入输入。缺失分隔、格式异常的案件单独标记并人工核查。

按案件和近重复文本分组划分训练、验证、测试集，防止同案不同版本跨集合。数据下载链接及密码在 eLearning 作业 4 页面。

WORKFLOW

六步完成判案服务

  1. 清洗与标注

    解析案由、引用法条和判决主文；“部分支持”需要结合诉讼请求与判项核对，不能仅凭关键词决定。统一 JSON 标签，人工抽查质量，再按案件分组切分。

  2. 先测未微调基线

    固定提示词和测试集，记录原始模型的 JSON 合法率、案由与方向正确率、法条匹配和延迟。保存逐案结果，作为微调前后的比较依据。

  3. 小规模 QLoRA 试跑

    使用 Transformers、PEFT、TRL 和 bitsandbytes，从原始指令模型以 NF4 4-bit 加载，训练 LoRA 适配器。可先尝试 rank 16、微批量 1、梯度累积及 1—3 个 epoch，验证后再调参。

    以上为建议起点。先统计案件 token 长度，选择能容纳事实的上下文；不能静默截掉关键诉求。训练只对目标回答计算损失，保存验证结果和适配器。

  4. 保留法条证据与测试记录

    在训练语料中建设案由和相似案件检索，可补充引用法条；不把测试案例加入索引。法条出处、版本及适用性必须可核对，微调不保证记住或正确引用所有法条。

  5. 封装本地 API

    基础模型和适配器在服务启动时加载，用 FastAPI 提供接口。Bearer Key 来自环境变量；对 JSON、四项字段和枚举校验。限制输出长度、并发与队列，实测总耗时在 120 秒内。

  6. 连接公网并按协议验收

    运行本地服务与 Cloudflare QuickTunnel，检查健康接口、错误 Key、正常请求及 10 个独立案例。提交后保持电脑开机不休眠，模型服务与隧道持续运行；地址变更后重新提交。
